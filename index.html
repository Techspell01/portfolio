Fishing Boat Safety System

Real-time distress and capsize detection for small-scale Kerala fishing boats.

Large vessels carry AIS. A traditional fishing boat that capsizes, floods, or loses engine power offshore has no way to tell anyone — families and the coast guard usually find out only when the boat fails to return. The maritime safety tech that exists is built for commercial fleets and priced for them.

The boat unit reads an IMU, a GPS module and a water-ingress switch, runs a classifier on the microcontroller itself, and relays the alert to shore over LoRa. No cloud, no cellular, nothing to subscribe to — it has to work where there is no signal, because that is exactly where boats get into trouble.

Where it fits

An automatic layer, not a replacement

Kerala’s Fisheries Department already distributes NavIC distress transmitters, and they work — but somebody has to press the button. This covers the cases where nobody can: a sudden capsize, a fisherman knocked overboard, an unconscious crew. That makes it a complement to infrastructure that already reaches the coast guard, which is also the pitch to Matsyafed or INCOIS.

  • ₹3,500–5,500parts for one boat unit
  • ₹3,000–4,000one shared shore gateway per harbour, one-time
  • ₹10,000existing NavIC transmitter, subsidised — the fisher contributes about ₹1,500
Build roadmap

Seven phases, sensing rig first

Phase 1 · nextSensing rig: ESP32, IMU, GPS, water switch, logging raw data to SD
Phase 2Collect data — real trips, safe bench tests, physics simulation
Phase 3Train the classifier, then shrink it to fit the microcontroller
Phase 4Offline relay: LoRa boat unit and shore gateway, then boat-to-boat mesh
Phase 5Dashboard — live map and status fed by the gateway
Phase 6Field test: waterproof enclosure, solar and battery, real trips
Phase 7Pitch to the Fisheries Department, Matsyafed or INCOIS

The dataset is the hard part. No public dataset of small-boat capsize events exists, so it has to be built from three sources: real logging trips in varied sea states, controlled edge cases reproduced safely on land, and a physics-based roll simulator for the events nobody should stage for real. Test splits hold out whole sessions rather than random windows — a random split leaks between train and test and makes the accuracy look better than it is.

Campus Hub

Events, QR ticketing and volunteer duty rosters for a college.

Students register for an event and get a signed QR pass. Coordinators open a “duty group”, project a rotating code, and watch volunteers appear on a live roster as they scan in from their own phones. The coordinator directory puts one tap between a student and WhatsApp, with the question already written — naming the duty and the event, so the reply is useful instead of “hi sir”.

The parts worth pointing at: a check-in QR that rotates every 30 seconds, so photographing the screen buys about a minute; correctness pushed into the database rather than into handlers, so two gates scanning one pass can’t both admit it; and hand-rolled auth — scrypt, opaque session cookies, only a hash of each token stored, so a database dump can’t be replayed as a login.

The problem underneath

A fest runs on WhatsApp and paper

Volunteer attendance is a register somebody loses. Passes are screenshots that get forwarded. Nobody knows who owns Stage Management until they’ve asked three people.

Which made the hard questions structural rather than visual. Can a screenshot of the check-in code be reused from a hostel room? Can one ticket get two people through the gate? What happens when a volunteer taps twice? Each is answered by a constraint in the schema instead of a check in a handler — a unique index, a conditional update, an HMAC bound to a time window.

  • ~10,000lines of TypeScript, one deployment
  • 19 / 6pages and API routes over one Postgres schema
  • 0.14–0.27spage load, after moving app and database into one region
